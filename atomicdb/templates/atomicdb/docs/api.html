API

Pace: the endpoints a script can call (query, request, live-request, frontier, my-queue, queue-bump, queue-cancel and map) take 5 requests a second from one address, with bursts of up to 50. Past that the reply is 429 with a JSON body and a Retry-After header, and nothing is lost: wait and send it again. The worker endpoints are not limited.

Request: POST /atomicdb/api/request with fen. budget picks a rung of the ladder and is optional, honoured for the accounts the explorer offers the depth slider to; budget=10000000000 is the slider's last stop, up to {{ subtree_cap }} searches of 128M below the position. username and password put the request on your account, which is what buys the notification when it lands, the affinity with your own workers and your place in the fair share. Without them the request is anonymous, which works, and is served like a click without a session. The reply names the live request on that position: task, its budget_nodes, and task_state, which is waiting while it is in the queue and searching once an engine has it. A FEN the tree does not have is seeded rather than refused. Session cookies are deliberately ignored here, so a page open in your browser cannot spend your queue behind your back.

Asked again after the first search has landed, a request buys the next rung of the ladder, exactly as a second click does, and once the 2B search has run, the searches below the position. Those replies say expanded, or saturated when there was nothing left to queue, with searches_queued, subtree_plies (how deep the deepest one is) and a message saying what was done. A script that only wants a position to have a search adds only_if_missing=1: the budget becomes a target (the rung you picked, or the first one). If a search that ran already covers it the reply is already-analyzed with completed_budget and nothing is queued; otherwise the request is queued as usual but never above the target. The check and the purchase happen together, so two scripts asking for the same position at the same moment cannot push it to the next rung. It asks about the position itself, so it cannot be sent with budget=10000000000.

There is no hourly limit on this door, same as the explorer button: what governs both is the per-person cap on queued requests above, and the per-account sharing of the service order. The pace above is about calls a second, not about how much you may ask for. Every call still leaves a receipt.

Your queue: POST /atomicdb/api/my-queue/ with username and password (your OpenBench credentials, same as a worker) returns your PENDING and LEASED requests: task ids, position keys, budgets, state, and the bump / cancel paths each row accepts. A logged-in browser can simply GET it. The ids are what scripted withdraw needed (P3, voted 28-Aug), and they plug into POST /atomicdb/api/queue-bump/<id>/ and POST /atomicdb/api/queue-cancel/<id>/ with the same credentials (form or JSON; undo=1 on cancel restores the row). The profile-page buttons are separate, session-guarded routes.

Query: GET /atomicdb/api/query?fen=... returns the position row (status, closure, score, point, backed_plies, best_move, the trust fields and the move list) plus an analysis block, which is null where no engine has looked yet. Inside that block, lines is the current pass, previous is the earlier pass, kept whenever it was wider than the one that replaced it, and passes is a compact summary per pass, newest first, which is what shows how the evaluation moved as the search went deeper. A position the tree does not have returns 404 here.

Roots: GET /atomicdb/api/roots returns the roots page as data: the start position, its first moves and the replies to 1.Nf3 in positions, and every named opening in openings. Each row has its key, label, line (the moves from the start position, in UCI) and its value now, then best_value and worst_value with their best_at and worst_at times (UTC) and their statuses. The values are centipawns from White's side, as on the page, with a proven win as +10000 or -10000 and a proven draw as 0; the score of query is from the side to move instead. since is when tracking began.

Each entry of moves carries floor. It is true for a move nobody has searched, outside the position's current lines, whose number would beat the last of those lines: the position does not use that number, and best_move never points at such a move. A client that picks from moves itself should skip those rows the same way.

Each entry also carries searched_nodes, the node budget of the deepest search that move's position has had, the depth column of the explorer, or null where no search has reached it, next to visits, the number of passes it has received. It counts the same searches only_if_missing does, so a request for a rung at or below searched_nodes with that flag comes back already-analyzed.

A request nobody has started yet is still yours to take back. Withdraw sits on the position and on every waiting row of your contributor page, and Clear my queue, at the foot of that list, empties everything you have waiting at once. Both are signed in controls rather than credential calls: they post to /atomicdb/queue/cancel/<task>/ and /atomicdb/queue/clear/ from a session. A request a worker has already started cannot be withdrawn, because the search is already running, and withdrawing a request somebody else also asked for only takes your name off: the request stays in the queue under them.
