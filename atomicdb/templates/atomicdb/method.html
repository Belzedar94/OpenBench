What "solved" means here

AtomicDB grows a persistent tree of Atomic Chess that the engine (Atomic-Stockfish) deepens node by node. A subtree becomes closed through three exact gates only:

  • TERMINAL: the position itself is checkmate, stalemate or a king explosion, verified by our own move generator (never by the engine).
  • MATE_PV: the engine announces a mate and its full line is re-verified move by move down to the terminal. A mate score alone never closes anything.
  • MINIMAX: three-valued backup over the COMPLETE list of legal moves (generated by us; the engine never filters legality).

Engine evaluations (the centipawn numbers) never close a node: they only order the exploration. Results are "practically solved", the standard used by the Fairy-Stockfish Solved-games wiki, and not game-theoretic proofs: position identity does not model repetition history (a known, declared limitation). A second-tier formal certification roadmap exists separately.

Contribute

Create an account via the OpenBench registration (instant activation), then run the analysis worker. You need python3 and an Atomic-Stockfish binary (build from source or grab a release):

git clone https://github.com/Belzedar94/OpenBench cd OpenBench/Client pip install requests chess python atomicdb_worker.py -U your_user -P your_pass -S https://belzedar.duckdns.org --engine path/to/Atomic-Stockfish.exe -T 8 --hash 1024

-T is the engine thread count per task (any number, no need to be a multiple of anything) and --hash is the engine hash in MB: higher budgets benefit from more hash, so if you can spare RAM, raise it. If you have the atomic Syzygy tablebases, add --syzygy dir1;dir2 and endgame positions will be closed exactly without costing you a single engine node. Every completed batch is credited to your username.
